# Data Khaos 数据工程补全路线图

> 版本：v1.0（基于 2026-08-31 代码实测盘点）
> 定位：README 的「第一~第六阶段」已完成，本文档规划**第七阶段及之后**的补全路径。
> 盘点方式：全量代码走查（非文档自述），266 个后端端点 / 43 条前端路由 / 14 个后端模块逐一核实。

---

## 一、总体判断

README 声称六个阶段全部完成。**这个说法在「功能覆盖」维度基本属实，在「能力落地」维度有 5 处断裂**。

关键区分：

- **真实可用**：`dquality` 规则引擎、`pipeline` 同步、`workflow` DAG 调度，都能真跑，不是摆设。
- **名存实亡**：行/列级权限、调度 DAG 依赖、三类任务执行 —— 界面能配、后端能存，但**查询/执行时完全不生效**。

后者比"没做"更危险：用户配置了策略以为生效了，实际没有 —— 属于**静默错误**，会直接导致越权看到数据或任务乱序跑出脏数据。

### 与文档不符的三处（需同步修正 README）

| 文档声称 | 代码实际 |
|---------|---------|
| 基于 RocketMQ 消息队列 | **零依赖**。Java/XML/YML 中零命中，仅出现在 4 个 .md 文件；服务间全为同步 `RestTemplate` |
| 统一权限体系：行级/列级权限 | 行/列策略**不参与 SQL 改写**，查询链路零引用 |
| 注册中心 Eureka / Consul | 需确认（盘点未发现相关依赖） |

## 二、已建成能力（真实可用，可作为后续建设地基）

| 能力域 | 现状 | 证据 |
|--------|------|------|
| 数据源接入 | 8 种类型真实可插拔 | `DsType` MYSQL/DM8/PG/HIVE/DORIS/CK/TRANSWARP/ORACLE；`AbstractJdbcConnector` 231 行共享实现，新增库只需加 `@Component` |
| 元数据治理 | 字段语义+字典+标准+落标校验全落地 | `meta_column` 含 biz_name/biz_comment/dict_type_code；`MetadataService` 落标校验（类型/长度/枚举三项） |
| 元数据检索 | 已覆盖业务名/说明/字典名 | `MetadataService:241-246` |
| SQL 血缘 | 表级自动解析 | `MetadataService:286-323` 正则解析 INSERT/CREATE...FROM/JOIN，**局限：无字段级，CTE/UNION/嵌套子查询会漏** |
| 采集保护 | 已治理字段不被覆盖 | `upsertColumn:445-473` |
| 语义建模 | 集市模型 STAR/雪花 + 指标 + 维度层级 | mart 模块 18 文件 |
| 可视化 | 仪表板（画布/版本/发布）+ 分析板 + 即席分析 | visual 模块 35 文件 / 56 端点 |
| 数据质量 | 5 类规则引擎真跑 | `QualityEngine` 366 行：NOT_NULL/UNIQUE/VALUE_RANGE/CUSTOM_SQL/CUSTOM_PROBE，经 SQL 审核后下发执行 |
| 数据管道 | 真同步 | `DbSyncEngine` JDBC 直连（500 批提交）、`DataXEngine`、`SeaTunnelEngine` |
| 工作流 | 真 DAG | `WorkflowRunner` 邻接表+入度、环检测、并行就绪队列、节点重试、失败快速跳过 |
| 调度引擎 | 真调度（非存字段） | `JobScheduler` `@Scheduled(5s)` + `CronExpression` 解析，到点投递线程池执行 |
| 前端骨架 | 43 条路由 **0 死路由** | 全部组件文件真实存在 |

**结论**：项目的"硬骨头"（规则引擎、DAG、数据同步、血缘解析）都啃下来了，且代码干净（全项目仅 2 处 TODO）。剩下的是**把已有的配置能力接到执行链路上**，以及**把 21 个未建设功能点补上**。

## 三、缺口清单

| # | 缺口 | 严重度 | 证据 |

## 四、阶段路线图

> 工作量按「1 名熟悉本项目的全栈」粗估，含联调，不含完整回归测试。

### 阶段七：可信性修复（约 5 人日）

**目标**：消灭所有"静默错误"。这类问题不报错但结果错，优先级高于任何新功能。

| 任务 | 改造点 | 验收标准 |
|------|--------|---------|
| 7.1 调度依赖引擎落地 | `JobScheduler` 扫描待触发任务时读取 `schedule_job_dep`，校验上游实例状态；上游未成功则跳过本轮并记录 `SKIPPED` | 配置 A→B 依赖后，A 失败时 B 不执行且状态可查 |
| 7.2 依赖环检测 | 借 `WorkflowRunner:345-384` 现成的环检测逻辑，在 `saveJobDep` 时校验 | 配置成环时拒绝保存并提示 |
| 7.3 REFRESH/SYNC/PUSH 真实执行 | `JobExecutor:121-125` 三个分支：REFRESH 走仪表板刷新、SYNC 复用 `pipeline` 引擎、PUSH 走 notification | 三类任务有真实执行日志和成功/失败结果 |
| 7.4 提取字段实现 | `DatasetService:156-158` 按模型关联的指标+维度生成字段列表 | "从模型提取字段"返回非空且字段正确 |

**阶段产出**：调度依赖真生效、无假成功任务、无 TODO 残留。

---

### 阶段八：权限引擎落地（约 12 人日）

**目标**：让 README 宣称的"行级/列级权限"真正生效。这是产品最核心的差异化卖点，当前是空的。

| 任务 | 改造点 | 验收标准 |
|------|--------|---------|
| 8.1 扩展 permission-api | `PermissionApiClient` 新增 `getRowPolicies(userId, dsId, db, table)` / `getColumnPolicies(...)`，返回策略 DTO | 接口可查询到当前用户在该表上的行/列策略 |
| 8.2 SQL 改写引擎 | 新建公共 SQL 改写组件（建议放 `common`）：行级 → 解析 WHERE 并 AND 追加谓词；列级 → 按策略做投影裁剪或脱敏函数包裹（如 `MASK_PHONE(col)`） | 单测覆盖：单表/多表 JOIN/子查询/聚合场景改写正确 |
| 8.3 接入查询链路 | `query`（SQL 工作台）、`visual`（即席分析/仪表板/数据集）、`mart`（指标查询）三条链路统一拦截改写 | 三条链路配了策略都生效；无策略时零性能损耗 |
| 8.4 脱敏策略可插拔 | 定义 `MaskFunction` SPI，内置手机号/身份证/邮箱/姓名，支持自定义 | 新增脱敏规则无需改核心代码 |
| 8.5 项目组管理界面 | 前端补 `ProjectGroupManage.vue`：成员管理、组内角色、资源绑定、能力位 | 17 个端点全部有界面，CRUD 闭环 |

**阶段产出**：权限策略"配置即生效"，有测试用例证明越权被拦截、敏感列被脱敏。

> 💡 这是整个路线图中**技术含量最高**的阶段。SQL 改写建议直接引入成熟 SQL 解析器（如 JSQLParser / Apache Calcite），自研正则极易在嵌套查询上出错 —— 项目里已有的血缘正则解析就有 CTE/UNION 漏解析问题，是前车之鉴。

## 五、建议的第一刀

如果只能先做一件事，做 **7.1 + 7.3（调度可信性）**，理由：

1. 工作量最小（约 3 人日），但消除的是**静默数据错误** —— 任务乱序和假成功会污染下游所有数据，而用户毫不知情。
2. 不依赖任何新组件，改动局限在 `schedule` 模块内，风险可控。
3. 完成后调度才真正可信，阶段八~十二的建设才有意义。

第二刀做 **阶段八权限引擎**，因为它技术风险最高（SQL 改写）、工作量最大，越晚做返工风险越大 —— 一旦查询链路被多处改动后再插入改写层，成本会翻倍。

**不推荐**先做 P3 的 21 个功能点：那是在不牢固的地基上盖楼。

## 六、风险提示

1. **SQL 改写是最大技术风险**。强烈建议引入 JSQLParser/Calcite 而非正则。项目现有的血缘解析（正则）已经暴露了 CTE/UNION 漏解析问题，不要重蹈覆辙。
2. **权限改造要防性能退化**。每次查询都拉策略会拖慢查询，需加缓存（Redis 或本地 Caffeine）+ 无策略快速跳过路径。
3. **社区版/企业版边界必须先定**。数据脱敏、操作审计在两个文档里归属冲突，开工前明确，否则可能做进社区版导致"白送"。
4. **README 需同步修正**。RocketMQ、行列权限、注册中心三处描述与代码不符，对外开源前必须改，否则是信誉风险。
